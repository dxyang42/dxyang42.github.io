DeepSeek-V4.1-Flash 精读（四）：没有新 RL 算法，Agent 为什么变强

报告在后训练章节开头先说了一句很不“发布会”的话：这次没有引入新的后训练算法。

配方仍是 SFT、RL，再加 on-policy distillation。优化方法也没有越出成熟做法。报告甚至把判断说得很重：在固定而普通的优化流程下，观测到的增益基本来自合成数据与环境在规模、多样性和可验证性上的改进。

这不是说 RL 不重要，而是说 RL 算法不是这次最稀缺的东西。Agent 要在真实系统里连续行动，首先得有足够多、足够难、能自动判分的任务；还得有跑得起百万级交互的基础设施。没有这些，换一个更漂亮的目标函数也只是对着贫瘠样本反复拟合。

也别把“数据工程”理解成多抓一些问答。Agent 的训练样本是一段真实执行：模型采取动作，环境改变状态，工具返回观察，验证器给出结果。这里每多一种任务、每换一种 scaffold，都会扩大策略实际见过的状态—动作分布。所谓数据规模，已经和可执行系统的规模绑在一起。

这也解释了为什么报告把大量篇幅给了容器、调度和中断恢复。对短问答来说，基础设施通常只影响训练速度；对长时程 Agent 来说，它还决定哪些轨迹能被完整采到、哪些失败能被复现、奖励是否可信。因此基础设施不是模型之外的后勤，而是训练方法的一部分。

训练单元不是一道题，而是一个三元组

报告的生产视角可以概括成三元组：task specification + environment + reference solution。

任务说明规定目标、初始状态和约束；环境负责让模型真的调用工具、改文件、运行命令并看到反馈；参考解答则帮助生成检查点与奖励信号。报告在质量审计时又把它形式化为 problem、environment、verification system：参考解答不是最终目的，最终必须落成一个能自动判断“做成没有”的验证系统。

这一区分很关键。普通指令数据只有“问题—答案”，Agent 数据却必须回答更多问题：依赖能不能装起来？起始仓库是不是正确状态？测试是否覆盖任务说明？旧功能有没有被改坏？有没有答案泄漏？模型能不能绕过测试骗分？

三元组里任何一项坏掉，RL 信号都会坏掉。题目含糊，模型不知道要做什么；环境不可复现，同一动作得到不同结果；参考方案或 verifier 有洞，模型就会学会钻洞。DeepSeek 因而同时按难度和正确性筛任务，还把 rollout 结果反过来用于复审：新一轮训练里暴露的新轨迹，本身就是环境质量的新证据。

两条任务管线：从真实查询来，也从零造出来

第一条管线从真实查询和失败出发。

通用 Agent 侧收集自愿返回的日常工作交互、负反馈和失败案例，再按观察到的接口去 mock SaaS、企业应用和专用后台。这里不是只改写一句 prompt，而是重建工具输入、输出结构、API schema、行为约束、用户交互方式和失败条件。好处是任务贴近真实分布，尤其能把线上弱点变成可重放、可专项训练的环境。

编码 Agent 也会从内部员工和外部伙伴的会话里筛复杂任务，或者挑模型表现差的任务，再按轨迹去重。真实查询提供的是“模型到底会在哪里摔跤”，比拍脑袋列能力清单更有价值。

第二条管线是从零生成。系统从达到 star 门槛的公开 GitHub 仓库出发，让多个专门 Agent 协作造题：先判断项目能否在容器内完整运行、能否自动验证，再选一个 turn 或 commit 作为起点，设计复杂实现方向和 fail-to-pass、pass-to-pass 检查点；随后配置依赖、工作目录、测试和题面，自测、清除答案痕迹，最后打包成新镜像层。

之后不是直接入库。多个求解 Agent 会实际做题，独立质检 Agent 同时看环境和轨迹，检查事实错误、题面与评分点错位、环境故障和可 hack 风险。失败后由修复 Agent 改环境、调难度，再重新验证。

我认为这里最值得借鉴的原则是：环境转换优先保留原意，而不是追求改得像一道新题。 从真实工作流转成可训练沙箱时，接口可以 mock，外部依赖可以容器化，敏感信息可以清除，但用户真正想完成的目标、关键约束和失败条件不能被“清洗”掉。否则 verifier 很稳定，训练的却是另一个问题。

多 scaffold 不是评测花样，而是训练维度

Agent 的最终行为由模型和 scaffold 共同决定。提示词、工具集合、上下文管理、压缩策略、动作协议变一点，rollout 分布就会变。只在一个 harness 里训练，模型很容易把对某套脚手架的适配误当成通用 Agent 能力。

报告因此沿两个方向扩 RL：一是增加累计 RL steps，二是增加 scaffold 数量。既联合训练多个 Claude Code 版本，也跨 OpenCode、Pi、DeepSeek Harness 的 Standard 和 PTC 模式做 rollout。本站已有一篇《DeepSeek Harness 和 Pi Agent》，专门讨论过这些运行时为什么不只是模型外壳。

实现上，rollout 被拆成 agent sandbox 与 worker container。前者运行 scaffold 和工具，后者提供与 scaffold 无关的控制层，把异构交互归一成统一轨迹格式，再和 trainer 通信。这样新增 scaffold 不需要修改底层 RL 算法。

但要克制解读：这些曲线说明“随着该训练流程推进，指标相关上升”，不是严格的因果消融。报告没有在完全相同算力、数据、初始化和评测条件下，只开关“多 scaffold”这一项。我们可以说结果支持这条工程路线，不能说它单独证明了增益全部由某个组件造成。

曲线里不连续的段落还对应另一个朴素做法：checkpoint merging。不同 scaffold、不同配置的 RL run 会走向不同优化路径，DeepSeek 把这些 checkpoint 合并，用来初始化下一轮 RL。它相当于把并行获得的能力重新汇总，再继续训练，既延伸有效 RL compute，也改善 token 效率。这仍不是新 RL 算法，更像训练编排层面的“接力跑”。

DSec：先让百万个环境可靠地跑起来

当并发沙箱来到百万级，瓶颈已经不是 PPO 或 GRPO 公式，而是数据中心能否调度、隔离和收拾这些会折腾系统的 Agent。DSec，也就是 DeepSeek Elastic Compute，就是这层生产基础设施。

它先把计算节点切成多个 shard，也叫 scale unit，隔离不同实验并缩小故障半径。调度上没有追求昂贵的全局强一致，而是让多个 placement engine 副本独立工作，根据近期观测做“足够好”的放置决定，接受最终一致性。

放松全局一致性不等于放弃安全。每个节点保留最后一道本地硬约束：如果新任务会让资源越过本地告警阈值，就直接拒绝。这种“中央近似、节点兜底”的设计，避免中央协调成为百万容器规模下的瓶颈。

单节点密度也做得很激进。DSec 用硬件支持的 sub-NUMA 分区，把 worker VM 绑定到独立 NUMA domain，再把容器 CPU 和内存限制在本地 NUMA 资源中。在可比负载下，每台物理节点可承载的并发存活容器，从约 1000 个提高到 2500 个以上，之后才出现可测的端到端退化。

高密度会干扰时间敏感评测，所以它又区分 latency-sensitive 执行类，降低非敏感任务的调度优先级，并约束同一超线程兄弟核上的任务类型。面对删系统文件、撞漏洞、偷包镜像答案的 Agent，则用 AppArmor 和 eBPF 网络策略隔离；环境被搞崩就记失败轨迹，把后果信号送回 RL。

异步 RL：吞吐上去了，统计偏差要还账

同步 rollout 最怕长尾：大多数样本早已完成，整组计算却在等最慢的一个。V4.1 的后训练基础设施把几乎所有 RL 和 OPD 任务改成异步生成，以足够高的并发掩盖长尾。系统按 sample 级调度：新完成样本数达到下一 prompt 对应的 GRPO group size，就发新任务，不必等待某个旧 group 全部结束。

异步会带来两个副作用。

第一是 length bias。短序列先完成，训练早期 batch 会被短样本占满。系统一方面按数据集限制并发，用来源配比间接控制长度分布；另一方面允许丢弃过早返回的短样本，让训练平滑进入稳态，避免模型过拟合“越短越容易被先训练”的偏差。

第二是 off-policy。部分 token 来自旧 checkpoint，样本不再严格由当前策略生成。系统通过调度和等待条件给最大 off-policy 比例设上界，再对陈旧度过高的 token 做 loss masking，不让它们贡献梯度。跨 checkpoint 的样本则保留各段 rollout 时的专家路由并拼接，而不是拿新模型重算。

它还支持 token 级中断，训练一旦拿够样本，进行中的生成几乎立刻停下；KV cache 和专家路由按 token 保存，切换 checkpoint 后从原处恢复。这些设计解决的是“如何不浪费已经跑出的交互”，而不是改写 RL 目标。

真正的结论：算法普通，不代表系统普通

这份报告最有价值的技术判断，是把 Agent 后训练的主战场从“再发明一个 loss”移到了任务与系统。

任务要贴近真实失败，也要能从仓库批量生成；环境要保留任务原意，还要可复现、可判分、抗作弊；rollout 要跨 scaffold；不同训练路径要能用 checkpoint merging 接起来；百万沙箱要靠 DSec 稳定承载；异步化省下的吞吐，还必须用 length bias 与 off-policy 修正来偿还统计代价。

所以“没有新 RL 算法”不是没有创新。更准确的说法是：这次创新主要发生在 RL 能吃到什么、在哪里跑、如何持续跑。当 Agent 训练从做几千道题变成运营一座自动出题、搭环境、验答案、跑轨迹、抓作弊的工厂，模型变强就不再神秘了。
