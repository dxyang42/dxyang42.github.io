DeepSeek-V4.1-Flash 精读（一）：百万上下文真正贵在哪里

发表于2026-09-12|更新于2026-09-12|人工智能
|浏览量:

“支持 1M 上下文”，现在很容易被读成一句简单的话：模型能一次塞进去一百万个 token。

但工程上真正该问的不是“塞不塞得进”，而是：塞进去以后，算一次要多少钱，放在哪里，下一轮怎么取，取出来又要搬多远？

DeepSeek-V4.1-Flash 技术报告最值得读的地方，不只是它把窗口做到 1M，而是它把长上下文成本拆成了一个完整系统问题。Attention FLOPs 当然重要，但它只是账单中的一项。Prefill 的计算、在线推理时常驻的 global KV、为了前缀复用而长期保存的 persistent KV，以及 HBM、主机内存、SSD 和互连带宽，合在一起才决定百万上下文是否真的用得起。

这一篇先把这张账单理清。具体怎么压，留到后面逐项拆。

先别急着谈 FLOPs：两种 KV 不是一回事

理解成本之前，先把报告里的两个词分开：runtime KV 和 persistent KV。

Runtime KV 是当前请求正在运行时要用的缓存。DeepSeek-V4 的注意力由两部分组成：一条看完整上下文的 global attention，另一条只看固定窗口的 Sliding-Window Attention（SWA）。SWA 的窗口固定，所以它占用的缓存不会随着整段序列无限增长；上下文足够长以后，真正占大头的是 global KV，包括 main KV 和用于索引的 indexer K。

这部分缓存服务时要随时参与计算，因此受 HBM 容量约束。HBM 快，但贵，而且空间有限。上下文从几千涨到一百万 token，哪怕每个 token 只多占一点，乘完都会变成一个很大的常驻量。

Persistent KV 则是另一笔账。它不是“这一刻做 decode 必须驻留在显存里的缓存”，而是为了以后复用某段前缀，把部分 KV 长期保存下来。它通常待在 SSD 或主机内存里，约束来自存储容量；等请求需要复用时，还要把数据加载、迁移到计算侧，因此又受 I/O 和互连带宽约束。

简单说：runtime KV 解决“现在算什么”，persistent KV 解决“以后别重算什么”。 前者主要卡 HBM，后者主要卡 SSD 和主机内存，但两者都会把压力传给数据搬运。

这一区分很关键。只说“KV Cache 降了多少”是不够的，因为你可能省了显存，却没有省下持久化容量；也可能少存了 SSD，却用大量重算把 prefill 成本重新买回来。

百万上下文的第一笔钱：Prefill

长上下文请求通常先经历 prefill：把整段输入读一遍，建立后续生成需要的状态。Agent 工作负载越来越“输入重”，历史对话、工具返回、代码、图片和文档不断累积，输出可能只是一小段，但输入已经非常长。

所以即便单 token decode 很省，首次吞下一百万 token 仍然不是免费的。报告直接把 prefill 称为计算昂贵的环节。DeepSeek-V4.1-Flash 的应对方式，是使用 Causal Encoder-Decoder（CED）架构：prefill 每个 token 激活 8B 参数，decode 每个 token 激活 16B 参数。

这里也容易误读。模型有 552B backbone 参数，另外还有 196B Engram 参数，但 MoE 模型不会每个 token 把所有参数都跑一遍。对部署成本更直接的数字，是每个阶段实际激活多少参数。把输入最重的 prefill 压到 8B，针对的正是长时程 Agent 那种“大量读、少量写”的负载结构。

来源：DeepSeek-V4.1-Flash 技术报告

第二笔钱：运行时 Global KV 要一直占着 HBM

Attention 计算做稀疏以后，一个反直觉现象会越来越明显：算力压力降下来了，存储压力反而显眼了。

因为只要全局分支还要从百万 token 中找信息，就得保留足够的全局状态。它未必对每个 token 做完整的两两 attention，但 global KV 仍会随序列长度增长。请求活着，它就要占着高价值的 HBM；并发请求一多，能同时服务多少条长会话，先被缓存容量卡住。

V4.1-Flash 把 global KV 压到 890 bytes/token，约为 V4-Flash 的 1/4。按线性关系做一个直观换算，一百万 token 对应的 global KV 约 890 MB。这个数字已经比前代小很多，但它依然说明：1M 不是界面上的一个开关，而是一段真实占用高速存储的状态。

我认为 890 bytes/token 比“支持 1M”更值得部署者盯住。窗口上限说明能力边界，每 token 缓存量才更接近容量规划：同样一块 HBM，究竟能放几个请求、留多少空间给权重与运行时、并发还能不能上去，都绕不开它。

第三笔钱：Persistent KV 把成本延伸到 SSD

长时程 Agent 不只跑一次。相同系统提示、固定知识前缀、已经完成的长轨迹，都可能希望下次直接复用。于是 KV 从一次请求里的临时状态，变成需要持续管理的资产。

这时容量问题从 HBM 扩散到 SSD 和主机内存。缓存越大，能保存的前缀越少；保存得再多，如果加载速度跟不上，GPU 还是会等数据。报告因此把 persistent KV、I/O 和互连带宽放在同一个部署问题里，而不是只比较 attention 算了多少次乘加。

V4.1-Flash 的 persistent KV 约为 V4-Flash 的 1/8。它背后的核心取舍不是一味“全存”或“全重算”，而是只持久化更值得保留的部分，对 SWA 状态采用 bounded replay：需要时只重放最近一个窗口的 token，近似重建缺失状态，用少量 prefill 重算换掉大量长期存储。

这也揭示了长上下文优化的本质：计算、存储和带宽不是三道独立题，而是可以互相兑换的三种预算。 少存一点，可能多算一点；压得更狠，可能降低精度；缓存放得更远，容量便宜了，搬运时间却上来了。

第四笔钱：Decode FLOPs 没暴涨，不代表系统成本消失

报告的 Figure 2 很抓眼球：上下文从 4K 扩展到 1M，长度增加 256 倍，V4.1-Flash 的单 token decode FLOPs 只增加约 25%。图中的计算量还按精度做了加权：BF16、FP8、FP4 分别按 1、0.5、0.25 计。

来源：DeepSeek-V4.1-Flash 技术报告

这确实说明稀疏与压缩设计有效：decode 端没有随着上下文长度近似线性爆炸。但它不能推出“百万上下文只贵 25%”。这个 25% 描述的是单 token decode 的加权计算量，不包含首次 prefill 吞下超长输入的全部代价，也不等于 KV 的 HBM 占用、SSD 持久化空间和缓存迁移时间。

换句话说，FLOPs 曲线回答“生成下一个 token 要多算多少”，却没有单独回答“为了能生成它，前面那一百万 token 的状态要放在哪、保存多久、何时搬过来”。后面这些，往往才是线上系统的吞吐瓶颈。

为什么带宽会成为隐藏账单

缓存不在计算设备上时，容量问题就会变成搬运问题。Persistent KV 放在 SSD 或主机内存里，确实比一直挤占 HBM 便宜；但请求再次命中这段前缀时，缓存必须被加载并迁移。报告明确指出，I/O 与互连带宽会限制这个过程。

这意味着“已经缓存”不等于“立刻可用”。如果迁移赶不上计算，设备会等缓存；如果大量长请求同时恢复，数据通道还会互相争用。即使单 token 的理论 FLOPs 很漂亮，端到端延迟与吞吐也可能由最慢的数据路径决定。

报告提到的系统处理方式很有代表性：把长生命周期的 global KV 与短生命周期的 encoder SWA KV 分开管理，缺失的 SWA 状态再通过 bounded replay 近似重建。我的理解是，这不是普通的显存优化，而是在给不同寿命、不同复用价值的状态安排不同层级。长上下文部署最终拼的，不只是模型会不会算，还包括系统知不知道什么值得常驻、什么值得落盘、什么重算更便宜。

真正的成本公式，是一条链

如果把报告的判断压成一句话，我会写成：

百万上下文成本 = Prefill 计算 + Runtime KV 的 HBM 占用 + Persistent KV 的存储占用 + KV 加载与迁移的带宽开销。

其中任何一项没处理好，1M 都可能只是“单请求能跑”，而不是“高并发、可复用、成本可控地跑”。V4.1-Flash 的路线也因此不是单点优化：CED 降 prefill 激活量，CSA2 做跨层 global KV 与索引复用，FP4 继续压 global KV，SWA Bounded Replay 用有限重算换持久化空间，推理系统再配合缓存分层、通信计算重叠和内核融合。

后续几篇会按这条链逐项展开。第二篇先看 CED：为什么同一个模型在 prefill 激活 8B、decode 激活 16B，以及这种不对称为什么适合输入重的 Agent。再往后看 CSA2、FP4 和 SWA Bounded Replay，分别怎样把运行时与持久 KV 压下来。

最后要留一个边界：支持 1M，不等于所有百万 token 任务都可靠。 技术报告证明的是模型具备这一上下文容量，并给出成本与系统设计；但具体任务能否在百万 token 中稳定找对信息、完成推理、维持多步行为，仍然要看任务结构和实际评测，不能从窗口长度直接推出答案质量。
