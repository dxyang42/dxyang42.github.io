DeepSeek Harness 和 Pi Agent，两个 Harness 走了不同的路

发表于2026-08-13|更新于2026-08-13|技术
|浏览量:

DeepSeek 最近发布了 Harness 开发者预览版 v0.1。它和 DeepSeek-V4-Pro 几乎前后脚出现，很容易被理解成一个官方编程助手，或者“DeepSeek 版 Codex”。

我觉得这个理解不太准确。

DeepSeek Harness 更像一套 Agent Runtime，默认带着 Web、TUI、Headless 和自动化接口，也提供工具、工作流、子 Agent、会话记录和权限策略。它想解决的不是“怎么让模型写几行代码”，而是“怎么把模型稳定地接到真实环境里”。

这件事其实早就有人在做。Pi Agent 就是其中很有代表性的项目。Pi 的介绍很直接，它是一个 minimal agent harness，意思是给你一个尽量小的 Agent 内核，然后让你自己决定它应该长什么样。

一个更重，一个更轻。一个想把整套运行时拆开，一个先给你一把小刀。

Harness 到底是什么

模型本身只负责生成下一步。它可以提出调用工具、修改文件、执行命令，但真正让这些动作发生的，是模型外面的那层系统。

这层系统要处理很多琐事。工具怎么注册，命令能不能执行，权限要不要询问，多个只读任务能不能并行，用户中途发来的新消息插到哪一轮，上下文太长时怎么压缩，任务失败后要不要重试，会话下次能不能接着跑。

这些东西合在一起，就是 Agent Harness。

以前很多项目会把 Agent Loop 写成一个循环。模型返回工具调用，就执行工具；把结果放回上下文，再请求模型；直到模型输出最终答案。几行代码能跑起来，但一旦任务变长，事情很快就不简单了。

模型到底看到了什么？刚才的工具结果有没有被截断？用户发来的转向指令有没有进入模型请求？子 Agent 使用了哪些权限？任务失败后，之前的状态还能不能恢复？

Harness 处理的就是这些“模型之外”的问题。

DeepSeek Harness 想做一块更大的底板

DeepSeek Harness 最醒目的口号是 Everything is a plugin，一切皆插件。

这里的插件不是普通意义上给软件加一个按钮。按照目前公开的项目资料，模型适配器、工具、提示词、Agent Loop、上下文压缩、会话存储、权限策略和界面，都可以通过插件进行替换或组合。

它的底层建立在 Cordis 微内核之上。运行中的 Harness 可以理解成一个 Context，不同的包往里面注册服务、事件和能力，最后再由配置文件组装出一套具体的 Agent。

同一套代码，可以组装成终端里的编程 Agent，也可以组装成 Web 应用、Headless 任务执行器，或者被其他程序通过 JSON-RPC 和 Python SDK 驱动。

这不是把一个客户端换个皮肤，而是在拆 Agent 产品的组成方式。

DeepSeek Harness 里还有 Agent Preset。标准模式、PTC 模式、极简模式和创造模式，并不是四个完全独立的产品，而是在同一个运行时里装配不同的工具、提示词和能力。

极简模式只给 Agent 少量工具，适合路径比较明确的任务。标准模式加入搜索、Skill、计划和子 Agent。PTC 模式允许模型编写 TypeScript 程序，把多次工具操作合并起来。创造模式会开放运行时检查和临时插件实验。

这套设计很重，但重得有理由。它希望同一个进程里同时运行编码 Agent、研究 Agent 和写作 Agent，每个 Agent 看到的工具和规则可以不同。

Pi 选择了另一种方向

Pi 的思路简单得多。

它先把终端 Coding Agent 做好，提供模型调用、文件读写、Shell、会话管理和基本的上下文处理。然后把更多能力交给 Extension、Skill、Prompt Template 和 Package。

Pi 默认不塞进 Sub-agent 和 Plan Mode。需要的时候，自己安装或写一个扩展就行。

这件事听起来像少做了功能，实际体验却可能更舒服。一个新项目最容易遇到的问题，不是能力少，而是默认行为太多。系统提示词太长，工具太杂，Agent 总在规划，简单任务反而要先开会。

Pi 把默认内核压得比较小，用户可以逐步加东西。想要权限门控，就装权限扩展。想要子 Agent，就装子 Agent 扩展。想改上下文压缩，也可以自己替换。

Pi 的官方文档有一句话我很喜欢，Change the harness, not your workflow。别为了适应一个封闭的 Agent 去改自己的工作流，直接把 Harness 改成你需要的样子。

这其实也是一种产品取舍。Pi 不急着把所有人的需求都塞进默认版本里。

两者真正的差别

两者都支持插件，但插件的作用范围不一样。

Pi 更像是在扩展一个 Agent。它让你修改工具、模型请求、系统提示词、会话行为、上下文压缩和终端界面。你仍然围绕着一个轻量的 Coding Agent 工作，只是这个 Agent 可以被改得很不一样。

DeepSeek Harness 则试图把整个 Agent 产品都变成可替换的部分。它不仅能改工具，还能改工具执行策略、会话存储、权限系统、Agent Loop 和界面。默认应用只是这套 SDK 的一个使用者。

这不是谁更先进的问题，而是抽象层级不同。Pi 把“我想要一个能改的 Agent”这件事做好。DeepSeek Harness 想把“我想组装一套 Agent 系统”这件事做好。

DSH 有一个 Pi 没有的重点，会话是运行事实

DeepSeek Harness 很重视 Session Log。

它不只保存用户和模型之间的聊天文本，还试图记录模型真正看见的内容，包括系统提示词、工具定义、模型请求、流式输出、工具调用、工具结果、上下文压缩、权限变化和取消原因。

这样做的好处是，任务失败后可以回放。开发者有机会回答一个很具体的问题，模型当时究竟看到了什么。

这对于普通个人使用可能有点过度，但对于 Agent 评测、企业审计和长期自动化，意义很大。Agent 出错时，光看最后一句“我已经完成了”没有用，需要知道它中间做了什么。

Pi 也有树状会话，可以恢复、分支和导出，个人使用已经很方便。只是 Pi 的重心更偏向交互式工作流，DSH 则明显在往可观测、可回放的运行时方向走。

安全方面，DSH 更像一个系统项目

Agent 一旦能运行 Shell，就不只是聊天工具了。它可能修改文件、安装依赖、启动进程，甚至访问工作区之外的内容。

Pi 的仓库明确提醒，默认情况下它没有内置的文件系统、进程、网络和凭据隔离，使用者需要自己放进 Docker、微型虚拟机或其他沙箱里。

DeepSeek Harness 则把权限和工具执行放进了统一的策略链，提供 workspace-write、审批、权限守卫和失败关闭等机制。文件工具、Shell 和子进程不应该各自有一套互相绕开的权限规则。

当然，DSH 现在还是 v0.1。设计文档写得完整，和经过长时间生产环境验证是两回事。尤其是创造模式允许 Agent 检查甚至临时改装自己的运行时，这种能力很有意思，安全边界也更需要实际测试。

谁更适合现在使用

如果只是想找一个好用的本地 Coding Agent，我会优先选 Pi。

它启动快，默认行为少，支持的模型和 Provider 很多，扩展方式也比较直白。接 DeepSeek、Kimi、Claude 或其他 OpenAI-compatible 模型都不麻烦。自己写几个 Extension，就能把它变成一个适合个人工作流的工具。

DeepSeek Harness 更适合拿来研究 Agent 基础设施，或者搭建一套更完整的内部 Agent 平台。它覆盖 Web、终端、Headless、RPC、多 Agent、工作流、权限和会话回放，想做的事情明显比一个命令行助手多。

代价也很清楚。概念多，代码量大，早期版本的 API 和插件生态还需要观察。你不只是安装一个工具，还要理解 Profile、Bundle、Preset、Context 和插件生命周期。

对于我这种经常需要换模型、改工具、接外部服务的使用方式，Pi 现在更顺手。它的内核小，改起来不容易迷路。

但 DeepSeek Harness 更值得持续关注。它把模型、工具和 Agent 产品之间的那层东西，公开成了一套比较完整的工程答案。

Harness 会成为模型厂商的新战场吗

模型价格会变，模型名字会变，今天的第一名过一阵子也可能掉下去。真正长期存在的，可能是模型如何进入工作流。

一个模型能不能稳定地读文件、改代码、调用工具、处理长任务，除了模型本身，还取决于外面的 Harness 怎么组织上下文，怎么调度工具，怎么处理失败，怎么保存状态。

DeepSeek 亲自做 Harness，说明它不满足于只提供一个 API。它想把自己的模型放进一个更完整的使用方式里，也想把 Agent 的运行时掌握在自己手上。

Pi 则代表了另一条路线。它不替用户决定 Agent 应该是什么，而是把改造权尽量交出去。

一个在做平台，一个在做工具箱。

这场比较暂时没有赢家。Pi 已经比较适合干活，DeepSeek Harness 刚开始展示它想把 Agent 做到什么程度。接下来真正有意思的，不是看谁的默认界面更漂亮，而是看谁能让开发者更容易造出一个自己愿意长期使用的 Agent。
